# 路线图

[English](ROADMAP.md)

当前版本之后计划做什么，以及每一项想到了什么程度。这里没有承诺，也没有日期。标为*已定*的条目有商定的方向；
*设想*表示讨论过、在纸面上判断可行；*未知*指出动手之前必须先回答的问题。

## 0.2.0 已完成

- **代码更容易上手。** 按子系统分包、统一排版、依赖只朝一个方向：geometry、chart、planet、sky、worldgen、universe、
  ground、flight、ship、space，然后是 waypoint、render 和 dev，接线在最上面。下层要用到上层时，只通过接线安装的
  host 接口。剩下朝上的引用只有几处指向 mixin，以及一处从 sky 指向 universe。
- **天体模型的第一部分。** 太阳、行星和卫星是同一种天体：运动（固定，或绕另一个天体的轨道）、半径、是否发光，以及
  决定引力、交接和船体重量的作用范围。固定的一对母星已经取消，一个星系可以只有一颗行星，一个世界的所有天体都在
  同一个维度里。
- **卫星**，由数据包定义，有完整地表；在地面上能看到天空中的其他天体。
- **太空中无人驾驶的飞船**会滑行减速，然后相对最近的天体停在原处，保存重进后也一样。

## 下一步：完成天体模型 *（已定）*

目标是打好一个以后加多人时不必重写的基础，同时保持改动小，以玩法为先。借鉴大型太空游戏管理宇宙的做法，定了三条
规则：天体的身份与它在哪里、存在哪里无关；天体的位置相对于它所属的天体给出；“有什么”与“由哪个进程模拟”分开。

| 部件 | 内容 | 是否必有 | 状态 |
|---|---|---|---|
| 身份 | 区域及其中的序号 | 必有 | 已完成：区域是宇宙网格的格子，母星系为区域 0，编号永不复用 |
| 运动 | 固定、绕另一个天体的轨道，或由物理驱动 | 必有，三选一 | 固定和轨道已完成 |
| 范围 | 半径、引力的强度和作用范围、飞船被交接的高度 | 必有 | 已完成 |
| 外观 | 从远处怎么画 | 必有 | 地表和光源已完成；模型和光点随空间站、卫星一起做 |
| 地表 | 真实区块：存储、形状、生成 | 可选 | 已完成 |
| 行为 | 发光、危险区、卫星的功能 | 可选 | 发光已完成 |

各种天体是部件的组合：太阳固定并发光；星球绕太阳、有地表；天然卫星绕星球；气态星球没有地表。

**飞船共用身份，不进天体目录。** 目录里每个天体的位置只由时间决定，任何进程都能自己算出来，不需要同步；飞船的
位置来自物理模拟。所以飞船仍是单独的记录：它和天体一样按区域加序号编号，在太空中时记下它相对的是哪个天体。

## 近期阶段顺序（最新排期）

1. **当前功能阶段收尾：** D1 气态巨行星 → 太空留船与可靠找回。可靠找回验收后，当前阶段结束。
2. **连续游玩体验优化与完整整合包：** 优先把现有玩法从开发测试条件整理成玩家能安装、正常开始并连续游玩的完整整合包。覆盖出生引导、准备、起飞、跨星航行、着陆探索/采矿、返航、留船找回和保存续玩；修复完整旅程中的阻断，不依赖开发命令或测试夹具。包格式、依赖配置与具体引导方案开工前确定。
3. **后续内容扩展：** 云和雨雪 → 真实恒星星空 → 气温、氧气、宇航服 → 小行星带（D2，最后）。这些内容全部排在完整整合包与连续体验阶段之后。

**阶段二必须包含地图与导航：** 星球地图（已探索地形、六面连续定位与地点标记）、恒星系地图（天体/轨道关系、目标选择、距离与航时、是否可着陆）、星际导航（星系分布、航线、家园与远征目的地）。三个层级共用标记并接到现有驾驶导航，支持“选星系 → 选星球 → 选着陆点 → 地表寻路”及返航。飞船标记跟随稳定身份和当前位置，保存重进后仍有效，不是离船时的旧坐标。首版不要求自动驾驶或复杂轨道转移规划，地图模组的六面适配须先验证。

阶段一可靠找回先提供最低限度船位定位与返回引导；完整地图系统放在阶段二，不提前扩大阶段一范围。整合包验收须通过正常玩家操作覆盖地图选目标、跨星航行、地表寻路、返航、找船和保存续玩。

本次为计划调整，不表示已开始实施或授权自动发布。当前 G2/C/D1 候选仍等待用户测试。

## 建立在天体模型之上

- **空间站：只有一个面的天体。** 空间站是只有一个平面、没有地形的天体。它有自己的区块，像星球一样到达和着陆，
  有没有船在附近都存在。它绕一颗行星运行，始终以同一面朝向行星；站上的重力指向这颗行星，所以行星在脚下，飞船从
  背向行星的一侧降落。除此之外它不能移动。它没有接缝，也没有折点：就是一座普通的人造建筑。走出边缘会朝行星
  落下。空间站可以写在数据包里，也可以由玩家在游戏中新建，先做数据包。*（已定）* 以后可以做失重的空间站：让这个
  天体没有引力，并给站上的人另一种移动方式。*（设想）* 待定：一个面最小能多小，有镂空的结构从远处怎么画。
- **人造卫星：一条轨道记录。** 以方块的形式建造并运上去，释放时变成存档记录，回收时变回物品；在算出的位置画一个
  小模型。第一版只做结构：发射、在轨、回收，以及夜空里的一个亮点。*（已定）* 卫星的用途以后再加；提到过导航、
  测绘和中继。*（设想）*
- **留在原地的飞船与可靠找回（已排在 D1 气态巨行星之后）。** 玩家在太空离船、回星球或换另一艘船远走后，应能定位、返回并重新登船；保存重进和服务器重启后也应成立。此项验收后结束当前功能阶段，先进入连续游玩体验优化与完整整合包阶段，再做后续内容；D2 小行星带仍最后。此为整体目标的排期更新，不表示完整玩法已实现或验收。
  目标是让飞船保留身份和位置，多艘船也能各在一处；完整的保留、休眠与定位方案仍超出已实现的重启恢复路径。
  当前源码（2026-11-03）：[`ShipHost.spaceDormancy()`](../src/main/java/dev/starfold/ship/ShipHost.java) 在生产中默认 **true**。
  [`ShipDormancy`](../src/main/java/dev/starfold/ship/ShipDormancy.java) 已支持唤醒重启后尚未加载的已保存太空船体：
  按当前时钟重算相对所属天体的位置，取得 `WAKING` 目标 tickets，在 Sable 加载或发布船体之前重定位。
  生产不会主动让已加载船体休眠；它们通过 [`SableTickets`](../src/main/java/dev/starfold/ship/SableTickets.java) 保留
  `ALWAYS` tickets。显式 sleep 请求属于开发探针。这次源码核对不代表完整离船、返回与重新登船玩法已验收。
- **有作用范围的引力。** 每个天体在一定距离内有引力，超出则为零；只计算最近的一个天体。*（已定）* 作用范围已经是
  天体的属性，决定交接高度和船体重量；无人驾驶的船相对最近的天体保持不动。剩下的是太空区域本身的引力，以及靠试飞
  重新调到达和悬停的手感。

## 暂缓事项

- **统一飞船控制信号。** 待排期。由玩家通过管道、电线或类似的连接件，把驾驶台和推进器等受控设备接入同一套信号系统，将当前按同船体自动选取推进器的方式改为显式接线。推进器等设备的控制输入宜与传感器的信号输出一起设计。连接介质和信号接口待定。

- **行星与卫星的开普勒椭圆轨道。** 待排期。考虑让数据包可选配置偏心率和近点方向，由半长轴推导周期，按时间计算轨道位置和速度。旧存档缺省为圆轨道。实现时需同步更新 Atlas 轨道线，并按近点、远点重新校验轨道间距和星系范围。

- **采矿平台与紧凑抽油机的外观及作业动画重设计。** 待排期。重新设计两台设备的方块模型与贴图，用动画表现采矿平台的钻掘，以及抽油机的建井和抽油过程。视觉方向与动画方案待定。详见 采矿专题。

- **远景 LOD 海水颜色与近景不一致。** 待调查。暖水海洋在近景呈青绿色，进入远景后看起来和普通海洋一样呈深蓝色，交界处出现明显色差。排查远景是否沿用了统一水色；修复后应保留两种海洋的水色差异，并消除同一片海水在近远景交界处的颜色突变。

- **远景 LOD 缺少水下植被。** 待调查。近处海底可见成片水草，进入远景后仍能看见海底地形，但植被在交界处突然消失。修复后，远景应保留水草等植被的大致分布，使同一片海底在近远景切换时自然过渡。

## 远期：大型多人 *（设想，现在不为它做任何实现）*

原版服务器在一个线程上依次运行所有维度，所以把区域做成维度并不能用上更多的核；而在同一个进程里给每个区域一个
线程，与 Create 和 Sable 一起使用时无法保证安全。如果大型服务器成为目标，可行的形式是多个进程：

- 每个区域（例如一个恒星系）是一个普通的服务器进程。跃迁把玩家和他们的船转到另一个进程，玩家直接连接过去。
- 一个轻量的协调进程负责登记（哪个进程运行哪个区域、每个玩家和每艘船在哪里）、执行交接，并保存各区域共用的
  内容：统一的时间，以及跨区域可见的记录，如留下的飞船、空间站和卫星。它自己不运行世界。
- 交接绝不能丢失飞船，也不能出现两艘：交接先被持久记录，双方都确认后才算完成。
- 协调进程停止时，各区域继续运行，只是不能跃迁。
- 单人和小型服务器仍是一个进程。交接一艘船是一个明确的操作，在那里直接执行，在集群上经由协调进程执行。

*未知：* Sable 船体能否连同方块、实体和乘员完整保存，并在另一个进程里恢复。留在原地的飞船需要同样的能力，所以
这个问题会在做天体模型时得到回答。天体模型会保持这件事所依赖的三个性质：身份由区域和序号构成、飞船可以存成
记录、位置只由时间决定。

"把区域做成维度、在同一个进程里用跃迁连接"也考虑过，已搁置：服务器的开销与现在的单一世界大致相同。
